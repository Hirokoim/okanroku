# 要件定義書：往還録（Ōkanroku）— 地図巡りツール

## 1. プロダクト概要

**プロダクト名**：往還録（Ōkanroku）

**一行コンセプト**：歴史上の人物が歩いた道を机上で管理し、現地での記録を1つの場所に蓄積するための、個人用フィールドノートツール。

「往還録」は、葛飾北斎・伊能忠敬・松尾芭蕉ら歴史上の人物の足跡を巡る個人プロジェクトを支えるためのWebアプリケーションです。全国に散らばる関連地点（当面は葛飾北斎「富嶽三十六景」の推定描画地点、全46図）を地図上で一元管理し、実際に現地を訪れた際の記録（写真・気づき・差分メモ）を1地点1レコードの構造化データとして蓄積します。

このツールが生み出すデータは、単なる旅の記録ではなく、将来の教材・データ基盤（歴史資本MCPサーバー構想）の原料となる「原本」として設計されています。現時点では本人のみが使う個人ツールですが、記録が構造化されて貯まっていくこと自体が、将来のあらゆる展開（研修化・ツアーアプリ・データ基盤化）の土台になります。

## 1-A. 実験レイヤーとの役割分担（2026-07-25追記）

開発着手にあたり、MulmoClaude（別途稼働中のローカルAIアプリ基盤）上に、「fugaku-36」という富嶽三十六景46地点分のスキーマ駆動コレクションを作成。現代地名・都道府県・訪問ステータス・写真・メモに加え、AIによる現代地イメージ生成アクションまで備えている。

この発見を踏まえ、役割分担を以下のように整理する。

- **fugaku-36（MulmoClaude）＝実地記録の主力**：MulmoServer（`mulmoserver.web.app`、Firestore経由のリモートホスト接続）経由でスマホから写真・気づきを送り、その場で記録する。「何を記録すると事業化に役立つか」を低コストで検証する実験場と位置づける。
- **往還録（本アプリ／Supabase）＝将来の本番プラットフォーム**：fugaku-36での実地検証を通じて固まった記録項目・使い勝手を、後から本番スタックに反映する受け皿とする。Phase1のうち「地点マスター」「地図表示」「進捗ダッシュボード」（本書6章参照）は、fugaku-36が当面その役割を代替できるため、優先度を下げる。

データそのものはfugaku-36から自動連携されず、知見（どの項目が有用だったか等）のみを本アプリの設計に反映する二段構えとする。

## 2. 対象ユーザーと課題・対策

**ペルソナ**：開発者本人。非エンジニア。葛飾北斎・伊能忠敬・芭蕉の足跡を実際に巡り、その記録を将来活用することを画策中。まだ一件も現地を訪れていない、これから巡礼を始める段階。

**課題①：地点管理が机上のリストのままでは追えない**
富嶽三十六景だけで46図、対象人物が増えれば地点数はさらに膨らむ。紙のリストやスプレッドシートでは、クラスタ（江戸市中・東海道・甲州道中など）ごとの動線設計や、訪問済み／未訪問のステータス管理がすぐに崩れる。

**対策①**：地点マスター管理・地図表示・進捗ダッシュボードを本アプリのPhase1機能として設計する。ただし現時点では、MulmoClaude上の`fugaku-36`コレクションが46地点分のマスタデータ・訪問ステータス・カンバン/カレンダー表示を既に提供しているため、当面はそちらで代替し、実地検証を経てから本アプリ側の設計に反映する（1-A参照）。

**課題②：現地記録が複数のアプリに散らばる**
写真はカメラロール、気づきはメモアプリ、GPS位置は記憶頼み——というように記録の置き場所がバラバラだと、後から「この地点で何を考えたか」を再構成するコストが跳ね上がる。特に「北斎の編集意図の仮説」のような一次的な気づきは、その場で書き留めないと失われやすい。

**対策②**：`records`テーブルに、写真・GPS座標・撮影日時・気づきメモ・差分カテゴリ・アクセス情報を1地点1レコードにまとめて記録できる構造を用意。現地では当面MulmoServer経由でfugaku-36に即時記録し、写真のEXIFからGPS座標・撮影日時を自動抽出する仕組みも活用することで、記憶頼みの部分を減らす。

## 3. システム機能要件

### 機能①：地点マスター管理（机上マッピング）

- 全地点データを一覧・地図上で表示する（地点名・関連人物・作品名・推定緯度経度・クラスタ区分・移動動線上の順序・訪問ステータス）
- 地図上にピン表示し、人物・クラスタ・訪問ステータスでフィルタできる
- 地点は手動で追加・編集できる（初期データとして北斎の46図＋追加10図をシードデータとして投入する）
- クラスタ（江戸市中・神奈川/東海道・甲州道中など）ごとに色分け表示する

### 機能②：現地記録入力（フィールドノート）

1地点1レコードで、以下の項目を記録する。往還録の「儀式」5ステップに対応した入力項目とする。

- 訪問日時・季節
- GPS位置（ブラウザのGeolocation APIで自動取得、手動補正も可能）
- 画角写真のアップロード（元絵の画像と並べて比較表示できるようにする）
- 差分カテゴリ（「変わった」「変わらない」「そもそも実景と違う」の3択＋自由記述）
- 気づきメモ（「なぜここをこう切ったか」の仮説を自由記述、Phase1はテキスト入力）
- アクセス情報（交通手段・所要時間・費用の簡易メモ）
- 編集意図の1行まとめ

### 機能③：進捗ダッシュボード

- 全体の訪問進捗（例：12/46地点訪問済み）を表示
- 人物別・クラスタ別の進捗内訳
- 直近の記録一覧（新しい順）
- 定点観測地点として指定した地点は、季節・時期違いの記録を並べて比較表示する

## 3-A. 継続利用設計

- **入力の手間**：現地での1地点の記録入力は3分以内で完了できることを目標にする（写真アップロード＋差分カテゴリ選択＋気づきメモの短文入力のみで完結する設計）
- **習慣化の仕掛け**：Phase1では通知・リマインダーは実装しない（個人利用のため必須ではない）。Phase2で「次に行く予定の地点」を思い出させる仕組みを検討
- **空白期間からの復帰**：アプリを開いたときに最初に見せるのは進捗ダッシュボード。「どこまで進んでいて、次にどこへ行くか」が一目でわかる状態にする
- **記録が貯まるほど価値が増す仕掛け**：定点観測地点の再訪比較（同じ場所の季節違い記録を並べる）を最低1つの仕掛けとして用意する

## 3-B. オンボーディング

- 初回起動時、地点マスターには北斎の全46地点があらかじめ投入された状態からスタートする（初期データゼロ問題への対策）
- 最初にやることは、地図上から1地点を選んで「次に行く予定」としてマークするだけ。3ステップ以内で最初の価値体験（地図が自分の巡礼計画になる）に到達する
- 現時点ではゲストモードは設けない。Googleログイン1つで足りる

## 4. 画面構成案

- **ログイン画面**：Googleログインのみ
- **地図トップ画面**：全地点をピン表示。人物・クラスタ・訪問ステータスでフィルタ可能。ピンをタップすると地点詳細へ遷移
- **地点詳細画面**：元絵の画像（あれば）と、現地記録フォームを1画面に表示。過去の記録があれば時系列で並べる
- **進捗ダッシュボード画面**：全体・人物別・クラスタ別の進捗、直近の記録一覧
- **記録一覧・編集画面**：これまでの記録を一覧・検索し、内容を編集できる

## 5. 技術スタック・アーキテクチャ方針

| 領域 | 候補・方針 |
|---|---|
| フレームワーク | Next.js（App Router） |
| DB/認証 | Supabase（Google OAuth、RLSで本人のみアクセス可） |
| 地図表示 | Leaflet.js（候補①・APIキー不要でコスト管理が容易）／Google Maps Embed（候補②・見た目に馴染みがあるがAPIキー管理が発生） |
| 画像ストレージ | Supabase Storage |
| 音声メモ | Phase1はテキスト入力のみ。Phase2で録音＋文字起こし（候補：Claude APIまたはWhisper API）を検討 |
| スタイル | Tailwind CSS |
| デプロイ | Vercel |
| 言語 | TypeScript |

## 5-C. プライバシーと安心感

- 現地記録には位置情報・写真という個人性の高いデータが含まれる。Phase1では**完全非公開**とし、RLSで本人のみが閲覧・編集できる設定にする。これは「原本は非公開資産として守る」という往還録全体の方針とも一致する
- 写真の保存先はSupabase Storageとし、無料枠内での容量方針を初期に確認する

## 5-D. 技術決定の記録（2026-07-25追記）

- **画像ストレージはSupabase Storageのまま採用**：Cloudflare R2（転送量無料）やVercel Blob（Hobbyプランは商用利用不可）も比較検討したが、DB・認証と同一ベンダーで完結し実装量が少ないことを優先。将来差し替えられるよう、アップロード・取得処理は`lib/storage.ts`に一本化した
- **Next.js 16では`middleware.ts`が`proxy.ts`に名称変更されている**（機能は同じ）。この環境のNext.jsバージョンに合わせて実装する必要がある
- **SQL Editorで直接テーブルを作成した場合、Table Editor経由と違い`GRANT`が自動付与されない**。RLSポリシーとは別に、`grant select on ... to anon, authenticated;`等を明示的に実行する必要がある

- [x] Google認証（ログイン・ログアウト）— 2026-07-25完了
- [ ] 地点マスターテーブルの作成＋北斎46地点分のシードデータ投入 — **保留**。fugaku-36（MulmoClaude）が同等の役割を代替中（1-A参照）
- [ ] 地図表示画面（Leafletでのピン表示、フィルタ機能）— **保留**（同上）
- [x] 地点詳細画面＋現地記録入力フォーム（写真アップロード・GPS自動取得・差分カテゴリ・気づきメモ）— 2026-07-25、簡易版として完了。人物マスタ（`figures`）＋記録本体（`records`）のテーブル設計・RLS・Storage・認証・最小フォームまで実装し、GitHub（Hirokoim/okanroku）にpush済み。地点マスターとの連携は次フェーズで検討
- [ ] 簡易進捗ダッシュボード — **保留**。fugaku-36のカンバン／カレンダー表示が当面代替

### Phase 2
**ゴール**：現地での記録がストレスなく行え、蓄積が資産として見える状態にする。

- [ ] 音声メモの録音＋文字起こし
- [ ] 定点観測地点の再訪比較表示
- [ ] 記録のMarkdownエクスポート（note下書き生成の土台）
- [ ] 進捗ダッシュボードの拡張（人物別・クラスタ別の内訳グラフ）

**ゴール**：個人ツールから、将来の複数人・複数プロジェクト利用にも耐える基盤へ拡張する。

- [ ] マルチユーザー対応の検討（チーム利用・共同記録）
- [ ] AR・位置情報を活用した表示（企画書で構想したAR展開の土台）
- [ ] データ基盤（歴史資本MCPサーバー構想）へのエクスポート・連携方式の検討

## 7. 非機能要件

- モバイル優先のレスポンシブ設計（現地でスマホから使うことを前提とする）
- 電波の弱い山道・史跡での利用を想定し、フォーム入力中のデータ消失を防ぐ工夫（送信前の一時保持など）をPhase2で検討する
- 位置情報・写真は個人の非公開データとして扱い、RLSで保護する

## 8. 競合差別化（代替手段との比較）

| 代替手段 | 弱点 |
|---|---|
| 紙のノート | 検索・進捗管理ができない。データとして二次利用しにくい |
| カメラロール＋メモアプリ | 写真とメモが分離し、地点との紐付けが手間。地図的な全体像が持てない |
| Googleマイマップ等の汎用地図ツール | ピン管理はできるが、差分カテゴリや編集意図といった往還録固有の記録項目を持たない |

往還録固有の強みは、「人物×地点×視点」という、このプロジェクトのために設計されたデータモデルを最初から持っている点にある。

## 9. 用語定義

- **往還**：人々が行き来した昔の街道・道そのものを指す言葉。プロダクト名の由来
- **原本**：本ツールが生成する非公開の構造化記録データ。note原稿・研修教材・ツアー台本・将来のデータ基盤の原料となる
- **儀式**：1地点での記録手順（現地を眺める→画角照合→気づきを記録→定点撮影→現地の人と一言、の5ステップ）を指す、往還録プロジェクト内の呼称
- **クラスタ**：地点を地理的にまとめた区分（例：江戸市中クラスタ、神奈川・東海道クラスタ、甲州道中クラスタ）

## 10. 将来のマネタイズ方針（参考・本ツール自体は非商用）

本ツールはPhase1〜2の間、無料・非公開の個人記録ツールとして運用する。ここで蓄積されたデータが、将来のサービス検討やデータ基盤（歴史資本MCPサーバー）の原料になる想定だが、それらの事業設計は本要件定義書のスコープ外とする（別途、往還録事業構想の企画書を参照）。
