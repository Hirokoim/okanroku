# MulmoClaudeを参照しながら開発するときの注意点

往還録（Supabase＋Next.js）を実装する過程で、`~/mulmoclaude`の`fugaku-36`コレクションを何度も参照した。うまくいった点・つまずいた点を、次に同じことをするときのために残す。

## 1. 「ビューの種類」を先に見分ける

MulmoClaudeの画面には性質の異なる2種類がある。

| 種類 | 例 | 参照の仕方 |
|---|---|---|
| 生のHTML/CSS/JS | `views/map.html`（地図画面） | ソースを読んで、**デザインだけ**移植できる。ロジックはMulmoClaude独自API（`window.__MC_VIEW`、写真取得エンドポイント等）に直結しているため、そのままでは動かない |
| `schema.json`から自動生成 | 詳細モーダル（スクリーンショットで見せてもらった画面） | ソースコードが存在しない。**構成（2カラムのラベル＋値、フィールドの並び）だけ**を見て自分で組む |

最初にどちらか確認しないと、「コードを流用しようとして無駄骨を折る」か「参考にできる情報を見落とす」かのどちらかになる。今回は`find`でファイルの有無を確認し、無ければ「これは自動生成」と判断した。

## 2. `schema.json`は「設計図」であって「実データ」ではない

`schema.json`には`composition_theme`（主題1語）・`historical_function`（当時の機能）・`why_fuji_visible`（なぜ富士が見えたか）といった項目が定義されていたが、**実際のitemファイル（`data/fugaku-36/items/*.json`）を見るとすべて空**だった。

schemaに書いてあることは「将来こう使うつもりだった」という意図であって、今のデータの実態ではない。**必ず実データのJSONを直接読んで、その項目が本当に埋まっているかを確認してから設計に取り込む**こと。逆に、実データにだけ存在する項目（`fuji_visibility`・`visibility_confidence`・`visibility_reason`など、schemaの`accessibility_class`等とは名前が違う）もあった。運用しながらフィールド名が変わっていく前提で見る必要がある。

## 3. フィールド名の食い違いに気をつける

同じ概念でも、`schema.json`（設計時点）と実データ（運用後）で名前が違うことがあった。

- `accessibility_class`（schema） vs `fuji_visibility`（実データ）
- `inaccessible_reason`（schema） vs `invisible_reason`（実データ、しかも未使用）

**「schemaにこの名前がある」で終わらせず、実データのキーで再確認する**。往還録側のカラム名を決めるときも、実データの値（`見える富士`/`見えない富士`/`心の中の富士`/`対象外`）を見てから`visible`/`not_visible`/`imagined`/`unjudged`という汎用値を設計した。

## 4. 画像・メディアファイルは「中身が良くても出典が無ければ使えない」

`data/fugaku-36/paintings/`に高解像度の元絵画像があったが、EXIF/XMPメタデータが一切無く、どこから取得したか追跡できなかった。北斎の絵自体はパブリックドメインでも、**画像ファイル（美術館の撮影データ）には別の権利問題がありうる**ため、出典不明のまま公開リポジトリのアプリに使うのは避けた。

代わりにMet Museum Open Access（CC0）から1点ずつ照合して取得し直した。ここで学んだこと：

- **API側が正しい情報（`isPublicDomain: true`等）を返していても、実際のURLが有効とは限らない**。46件中1件（46番「諸人登山」）は`primaryImage`のURLがMet側で404になっていた。`curl`で全件疎通確認して初めて気づいた
- 検索結果には同じ図の異なる刷り（複数の`object`番号）が混ざる。タイトルの文字列一致だけで機械的に当てはめず、**日本語タイトルとの対応を1件ずつ目視確認**した

## 5. 単一ユーザー設計と複数ユーザー設計は、データの持ち方が根本的に違う

MulmoClaudeの`fugaku-36`は1人（ひろこさん）が使う前提なので、1つのアイテムJSONに「訪問ステータス」「訪問日」「訪問時の緯度経度」「写真」まで全部同居している。往還録は複数ユーザー設計なので、これをそのまま真似ると破綻する。

- 「比定地」（誰が見ても同じ、`locations`）と「訪問した実測地点」（ユーザーごとに違う、`record_photos`）を最初から別テーブルに分けた
- 「訪問済みかどうか」は共有テーブルに持たせず、そのユーザー自身の記録が存在するかで導出する

**MulmoClaude側の1ファイル1レコードの構造を見て「便利そうだからこの形にしよう」とせず、「これは単一ユーザー前提だからこう出来ている」という前提を必ず疑うこと。**

## 6. 用語・命名はそのまま借りて良い

データ構造は上記の通り作り直したが、**日本語の用語や命名は積極的に踏襲した**。

- 富士の見え方の4分類（見える／見えない／心の中／未判定）
- 「令制国・場所」という地名の切り方（クラスタ名）
- 「比定地」という言葉そのもの

ここは車輪の再発明をしない方が良い部分だった。北斎の作品世界に関する語彙は、MulmoClaude側で既に実用を通して練られている。

## 7. 実装前に「本当に参照できるものがあるか」を確認する

「MulmoClaudeにもあるはず」で作業を始める前に、`find`や`ls`で実在を確認してから読みに行く、という手順を毎回踏んだ。無いものを探しに行って時間を使うより、無ければ無いと早めに分かった方が早い。
