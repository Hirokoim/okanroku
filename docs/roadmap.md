# 往還録 開発ロードマップ（Phase1〜3）

`docs/requirements.md` 6章の開発フェーズ計画を、**進め方の手順**として整理したもの。完了/未完了の実データは6章が正、こちらは「残りをどの順番で・どう確認しながら進めるか」の手引き。

---

## 1. 作業の標準サイクル

**1タスクごとに、必ずこの順で進める。** 複数タスクをまとめて実装してから一度に確認する、はやらない。問題が起きたときにどれが原因か分からなくなるため。

```
① 方針の提示  →  ② モックアップ（必要な場合のみ）  →  ③ 承認  →  ④ 実装  →  ⑤ 検証  →  ⑥ 記録
                        ↑                                                    │
                        └──────── 直したい点があれば戻る ────────────────────┘
```

### ① 方針の提示

「何を・なぜ・どこを変えるか」を3行で先に示す。このリポジトリには`vibe-coding-workflow`スキルがあり、この形式が定められている。コードを書く前に必ず通す。

### ② モックアップ（必要な場合のみ）

作る/作らないの判断基準は下記。**モックアップは見た目の下書きであり、実際に動くコードではない。** 直したいところはチャットで言葉で伝えれば、その場で作り直す。何度でも往復してよい。

| モックアップを作る | 作らずに直接実装する |
|---|---|
| ユーザーが直接触る新しい画面・新しい操作導線 | データベースのスキーマ変更・RLSポリシー |
| 見た目や情報の出し方に選択肢がある（配色・レイアウト・出し分け） | 既存画面への軽微な項目追加 |
| 一度決めると後から直しにくいもの（オンボーディングの流れ、導線の分岐） | 裏側の処理（EXIF抽出・天気取得など画面に出ない部分） |

迷ったら「これは今すぐ見せられる形にできるか」で判断する。

### ③ 承認

「この内容で進めてよいか」で一度止める。承認前に次へ進まない。

### ④ 実装

1回の変更は1つの目的に絞る。依頼されていない「ついで」の変更はしない。

### ⑤ 検証 — ここが最も混乱しやすいので明示する

**このプロジェクトでは、私（Claude）が確認できる範囲とできない範囲がはっきり分かれている。** 残りのタスクはほぼ全てログイン状態を必要とするが、開発環境からGoogleログインができないため、**実データでの最終確認は必ずご本人が行う必要がある。**

| 私が確認できること | ご本人にしか確認できないこと |
|---|---|
| ビルド・型チェックが通るか | ログイン後に実データで正しく動くか |
| 未ログイン状態の画面（ログイン促し等） | 自分の記録が正しく保存・表示されるか |
| 仮データを流し込んだ検証用ページでの描画・操作 | RLSが意図通り効いているか（他人のデータが見えないか） |
| 外部URLの疎通（画像リンクが有効か等） | 実際の写真・GPSでの挙動 |
| SQLの構文・実行順序の妥当性 | SQLの実行そのもの（Supabaseへのアクセス権が無い） |

**私が「検証しました」と言うときは、上の左側の範囲だけを指す。** 右側は必ずお願いする。逆に、私が確認できる範囲を確認せずに「できました」と報告することはしない。

### ⑥ 記録

- スキーマ・RLSの変更 → `docs/sql/` にSQLを、検証結果は `docs/supabase-schema-status.md` に追記
- 設計判断（なぜそうしたか）→ `docs/requirements.md` 5-E章に追記
- 完了したタスク → `docs/requirements.md` 6章のチェックを更新

## 2. フェーズの区切りで立ち止まる

各Phaseの最後、および**大きな設計判断をした直後**に、一度作業を止めて再評価する。このプロジェクトでは実際に、後から見直して以下のような誤りが見つかっている。

- 参照していた要件定義書が古い方だった（正典が別ファイルにあった）
- 分類データの置き場所が根本的に間違っていた（記録側ではなく地点側が正しかった）
- 外部APIが「有効」と返すURLが実際には404だった

**「一度作ったものは正しい」と仮定せず、次のPhaseに進む前に前提を洗い直す。** 具体的には、要件定義書の記述と実装が食い違っていないか、前Phaseで決めた設計判断が今も妥当か、を確認する。

## 3. Phase 1（MVP）：残タスク

**ゴール**：北斎46図に絞り、地点を地図で見て、現地で1件記録を保存できる状態にする。

データモデル・地図画面・地点詳細画面は完成済み。残るは「現地での記録入力」まわり。

### 進める順番

```
(A) locations.cluster を埋める        ← 独立。いつでも可
(B) 記録フォームへの location_id 連携  ← ここが全ての起点
     ↓
(C) 写真EXIFのGPS・撮影日時の自動抽出
     ↓
(D) 複数写真の一括取り込み動線
     ↓
(E) 簡易進捗ダッシュボード            ← (B)完了後でないと数字が全部0になる

(F) 天気の自動取得        ← (B)〜(D)と並行可
(G) 入力中データの一時保持 ← 並行可
```

**(E)ダッシュボードは(B)より後**。進捗は「`location_id`が設定された記録の地点の種類数」で数える設計（機能③）のため、(B)が終わるまでデータが存在せず、実装しても全て0件で検証できない。

### タスク別の確認方法

| 項目 | モックアップ | 検証（左：私／右：ご本人） |
|---|---|---|
| (A) `locations.cluster`を埋める | 不要 | SQLの妥当性／実行と、地図のクラスタフィルタでの見え方 |
| (B) `location_id`連携 | **要**（近傍候補の提示UI。前回作成済みのものを流用可） | 仮データでの描画／実際の写真で候補が正しく出るか |
| (C) EXIF自動抽出 | **要**（GPSが取れなかった時の代替入力の導線のみ） | 抽出処理の単体動作／実際の写真での成功時・失敗時の両方 |
| (D) 複数写真の一括取り込み | **要**（「5枚は3地点ぶんのようです」の確認画面） | 仮データでの分岐表示／実際に3地点分をまとめて投入 |
| (E) 進捗ダッシュボード | **要**（数字の見せ方・クラスタ別内訳の並べ方） | 仮データでの描画／実データで数字が合っているか |
| (F) 天気の自動取得 | 不要 | API疎通／保存後に天気が入っているか。**圏外時に保存がブロックされないこと**（5-E⑥） |
| (G) 入力中データの一時保持 | 不要 | 実装の妥当性／入力途中でタブを閉じ、再度開いて内容が残るか |

## 4. Phase 2：現地記録の充実・複数ユーザーの解禁

**ゴール**：現地での記録がストレスなく行え、蓄積が資産として見え、他ユーザーとも記録を見せ合える状態にする。

**着手前に必ず読む**：Phase2では画面が一気に増える（要件定義書4章の5〜10・13）。**画面の数だけルートを作らない**という方針が要件定義書5-Aにあるので、実装に入る前に目を通す。ここを外すと、あとから戻すのが最も高くつく。

### 進める順番

```
(1) 解説レイヤーを1地点だけ作る    ← 最優先。作ってみないと面白さが判断できない
     ↓ 面白ければ
(2) 残り45地点へ広げる

(3) 「旅」の状態（計画済み）の保存と再開導線 ┐ (3)が(4)の土台。
(4) 現地モード（近接検知・到着判定）         ┘ 順番を入れ替えない

(5) 伊能忠敬 or 松尾芭蕉のデータ投入 ┐
(6) 人物ごとのアクセス権を適用       ┘ 必ずセットで行う
(7) 人物ごとの導入演出               ← 北斎ぶんだけなら先に作ってよい

(8) 元絵と現地写真の並列比較
(9) 定点観測の再訪比較
(10) 音声メモ
(11) 進捗ダッシュボードの拡張
(12) Markdownエクスポート
(13) 他ユーザーの公開記録閲覧      ← 最後。自分のデータが貯まってからの方が確認しやすい
```

**(1)を最優先にする理由**：46地点×解説の執筆量がこのレイヤーの本当のコストであり、面白いかどうかは実際の文章を読むまで判断できない（要件定義書 機能⑥に明記）。プレースホルダ文字のモックアップでは判断材料にならないため、**1地点だけ本物の文章を書いて読み比べる**ところから始める。第26景でトーン比較（随筆調／講談調）は実施済み。

**(3)を(4)より先にする理由**：現地モードは「計画した旅の続きから始まる」ことが前提で、机上と現地のあいだには数日の断絶がある（要件定義書4-B）。旅の状態を保存する土台が無いまま到着判定だけ作ると、アプリを閉じた瞬間に進行が消え、現地で最初から操作をやり直すことになる。**断絶に耐えることが現地モードの価値そのもの**なので、順番を入れ替えない。

**(5)と(6)をセットにする理由**：アクセス権のSQL（`docs/sql/`ステップ12）は破壊的変更で、適用すると権限を持たないユーザーには地図が空になる。北斎しかデータが無い状態で適用しても「複数人物が地図に重なる」という肝心の効果を確認できず、リスクだけを負う。

| 項目 | モックアップ | 検証（左：私／右：ご本人） |
|---|---|---|
| (1)(2) 解説レイヤー | **要**（ただし本物の文章で。仮の文章では判断不能） | 文章の下書き／読んで面白いかの判断 |
| (3) 旅の状態の保存・再開 | **要**（ダッシュボードでの「計画済み」の見せ方と再開導線） | 仮データでの描画／**日をまたいで再開し、続きから始まるか** |
| (4) 現地モード | **要**（探索中／到着／手動申告の状態遷移） | 実装の妥当性／**実際に現地で、圏外時も含めて動くか** |
| (5) 人物データ追加 | 不要 | データの妥当性／SQL実行 |
| (6) 人物ごとのアクセス権 | **要**（人物選択画面。未購入人物は現設計では完全非表示） | SQLの妥当性／**2アカウントで権限の有無を実際に確認** |
| (7) 人物ごとの導入演出 | **要**（初回の流れ。スキップ導線を必ず含める） | 仮データでの描画／2回目以降スキップされるか・読み返せるか |
| (8) 元絵と現地写真の並列比較 | **要** | 仮画像での描画／実際の現地写真での見え方 |
| (9) 定点観測の再訪比較 | **要**（同一地点の複数記録の並べ方） | 仮データ／同じ地点で2件以上記録した状態 |
| (10) 音声メモ | **要**（録音中／文字起こし中／完了の状態遷移） | 実装／実機での録音精度 |
| (11) ダッシュボード拡張 | **要**（グラフの種類） | 仮データ／実データ |
| (12) Markdownエクスポート | 不要 | 出力形式／noteに貼って崩れないか |
| (13) 他ユーザーの公開記録閲覧 | **要**（他ユーザー記録の並び方） | RLSの妥当性／**2アカウントで公開・非公開を実際に確認** |

**(6)と(13)は必ず2アカウントで確認する。** 自分のアカウントだけでは「他人に見えていないこと」を確認できない。ここを飛ばすと、公開してはいけないデータが見える状態のまま気づけない。

**(4)は必ず現地で確認する。** 到着判定と圏外時のふるまいは、机上のブラウザでは再現できない。手動での到着申告が使えることまで含めて、実際に現地で確かめる（要件定義書 機能⑦）。

## 5. Phase 3：プラットフォーム化

**ゴール**：より多くの巡礼者を受け入れられる基盤へ拡張する。

| 項目 | モックアップ | 備考 |
|---|---|---|
| 新規ユーザー獲得・オンボーディング施策 | **要**（初回起動時の導線） | 第三者に実際に触ってもらう検証が必須 |
| AR・位置情報を活用した表示 | 技術検証を兼ねた簡易プロトタイプが実質モックアップになる | 現地での実機テストが必須 |
| データ基盤（歴史資本MCPサーバー構想）への連携 | 不要 | 連携先の要件が固まってから着手判断 |

Phase3は現時点で詳細を詰めるには時期尚早な項目が多い。**Phase2が一段落した時点で、この一覧自体を再評価してから優先順位を決める。**
