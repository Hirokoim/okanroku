## 優先度1：現状RLSポリシーの検証

### なぜこれが最優先か（初版より重要度を格上げ）

[page.tsx:12-17](../app/page.tsx:12-17)の記録取得クエリには`.eq('user_id', user.id)`のような絞り込みが**一切ない**。表示件数の制御をRLSに100%依存している。

つまり、RLSが無効だったり決め打ちだったりした場合、2人目のユーザーがログインした瞬間に全員の記録が互いに見える状態になる。単なる現状確認ではなく、公開前に必ず潰すべきセキュリティ確認。

### 実行するSQL

SQL Editorで実行し、結果を貼ってください。

```sql
-- ① RLSがそもそも有効か（最重要。falseなら現状ポリシーは全て無効＝素通し）
select relname, relrowsecurity, relforcerowsecurity
from pg_class
where relname in ('records', 'figures');

-- ② ポリシー定義
select tablename, policyname, permissive, roles, cmd, qual, with_check
from pg_policies
where tablename in ('records', 'figures');

-- ③ recordsのカラム定義（user_id・is_publicの有無、NOT NULL制約）
select column_name, data_type, is_nullable, column_default
from information_schema.columns
where table_name = 'records'
order by ordinal_position;

-- ④ figuresのカラム定義
select column_name, data_type, is_nullable, column_default
from information_schema.columns
where table_name = 'figures'
order by ordinal_position;

-- ⑤ Storageバケットのポリシー（0-4の通り、写真も複数ユーザー対応が必要）
select policyname, cmd, qual, with_check
from pg_policies
where schemaname = 'storage' and tablename = 'objects';

-- ⑥ user_idがnullの既存行がないか（優先度2のバックフィル対象の確認）
select count(*) as total, count(user_id) as with_user_id from records;
```

### 判定基準

| ①の結果 | 判定 |
|---|---|
| `relrowsecurity = false` | **RLS未有効。最優先で有効化**（`alter table records enable row level security;`）。ポリシーの中身以前の問題 |
| `relrowsecurity = true` | ②へ進む |

| ②の`qual`の中身 | 判定 |
|---|---|
| `(auth.uid() = user_id)` のような列参照 | 一般化済み。優先度2はRLS張り替え不要、`is_public`列追加のみ |
| 特定UUIDの決め打ち（`auth.uid() = 'xxxx-...'::uuid`） | 移行が必要。優先度2をフル実施 |
| ポリシーが0件 かつ ①がtrue | 誰も読み書きできない状態。優先度2でポリシーを新規作成 |

判定結果は末尾「作業ログ」に追記する。

## 優先度2：`records`テーブルのスキーマ更新

[record-form.tsx:35](../app/record-form.tsx:35)が既に`user_id: userId`を挿入しているので、列自体は存在する可能性が高い。上記⑥・③の結果を見て分岐。

### 2-1. 列の追加とバックフィル

```sql
begin;

alter table records add column if not exists user_id uuid references auth.users(id);
alter table records add column if not exists is_public boolean not null default false;

-- 既存行のuser_idがnullなら本人のIDで補完（⑥でnullが0件なら不要）
-- auth.usersでUUIDを確認してから実行すること
update records set user_id = '<ユーザーAのUUID>' where user_id is null;

-- バックフィル後にNOT NULLを付ける（下記の注意点を参照）
alter table records alter column user_id set not null;
alter table records alter column user_id set default auth.uid();

commit;
```

**なぜNOT NULLを付けるか**：`auth.uid() = user_id`というRLSは、`user_id`がnullの行に対してnull（＝真ではない）を返すため、その行は**誰からも永久に見えなくなる**。エラーも出ないので気づけない。将来の挿入漏れを防ぐため制約で塞ぐ。`default auth.uid()`も同じ理由の二重の保険。

### 2-2. RLSポリシーの張り替え（優先度1で決め打ちだった場合のみ）

```sql
begin;

drop policy if exists "<①②で確認した既存ポリシー名>" on records;

create policy "records_select_own" on records
  for select to authenticated using (auth.uid() = user_id);
create policy "records_insert_own" on records
  for insert to authenticated with check (auth.uid() = user_id);
create policy "records_update_own" on records
  for update to authenticated using (auth.uid() = user_id) with check (auth.uid() = user_id);
create policy "records_delete_own" on records
  for delete to authenticated using (auth.uid() = user_id);

grant select, insert, update, delete on records to authenticated;

commit;
```

**`begin; ... commit;`で囲む理由**：`drop`が成功して`create`が失敗すると、RLS有効＋ポリシー0件＝**自分の記録も含め全件アクセス不能**になる。トランザクションにしておけば途中で失敗しても元に戻る。実行後は必ずアプリで記録の表示・保存を確認すること。

`is_public`は**列を用意するだけ**。公開読み取りのRLSポリシーはPhase2まで作らない（要件定義書:130, 153）。

## 優先度2.5：Storage（写真）のRLS検証【新規・引き継ぎ書に記載なし】

引き継ぎ書の「画像ストレージは変更しない」は**保存先とライブラリ構成の話**であって、アクセス制御まで現状維持でよいという意味ではない。ここは3つの文書すべてが触れていない穴。

[storage.ts:9](../lib/storage.ts:9)は`${userId}/{uuid}.{ext}`というパスで保存している。パスがユーザーごとに分かれている設計なので、バケットのポリシーも同じ粒度で絞る必要がある。優先度1の⑤の結果を見て、決め打ちや素通しになっていれば以下に張り替える。

```sql
begin;

-- 自分のフォルダ配下のみ読み書きできる
create policy "photos_own_folder_select" on storage.objects
  for select to authenticated
  using (bucket_id = 'photos' and (storage.foldername(name))[1] = auth.uid()::text);

create policy "photos_own_folder_insert" on storage.objects
  for insert to authenticated
  with check (bucket_id = 'photos' and (storage.foldername(name))[1] = auth.uid()::text);

create policy "photos_own_folder_delete" on storage.objects
  for delete to authenticated
  using (bucket_id = 'photos' and (storage.foldername(name))[1] = auth.uid()::text);

commit;
```

**Phase2への申し送り**：記録を`is_public=true`で公開したとき、記録本文は他ユーザーに見えても**写真は上のポリシーで弾かれて見えない**。公開記録の写真をどう見せるか（公開用パスへ複製する／署名付きURLをサーバー側で発行する等）はPhase2の機能⑤設計時に決める必要がある。ここでは列と本文だけ先に用意し、写真の公開は積み残しとして明示しておく。

## 優先度3：`figures`（人物マスタ）の共有マスタ化

0-3の判断が「人物マスタのまま据え置き」なら、シードデータ追加は不要でRLS変更のみ。

```sql
begin;

drop policy if exists "<既存ポリシー名>" on figures;

-- 全ログインユーザーが読める
create policy "figures_select_all" on figures
  for select to authenticated using (true);

-- 書き込みは管理者のみ（Phase1はロール管理を作らないため、メールアドレスで代用）
create policy "figures_admin_write" on figures
  for all to authenticated
  using (auth.jwt() ->> 'email' = '<ユーザーAのメールアドレス>')
  with check (auth.jwt() ->> 'email' = '<ユーザーAのメールアドレス>');

grant select on figures to authenticated;

commit;
```

**2点の注意**：

1. メールアドレスの決め打ちは、優先度1で問題視している「固定ID決め打ち」と本質的に同じ手法。要件定義書5-B（:129）が「Phase1では実質ユーザーAのみ運用で管理し、ロール管理は作らない」と明示的に許容しているので**意図的な割り切り**だが、`figures`に他人が書き込める必要が出た時点で`profiles.role`のようなロール列に置き換える。この一文を要件定義書5-Bに追記しておくとよい。
2. **実際のメールアドレスをこの手順書やSQLファイルに書いてコミットしないこと**。GitHubの公開リポジトリ（Hirokoim/okanroku）にメールアドレスが残る。上記のままプレースホルダにしておき、SQL Editorに貼るときだけ実値に置き換える。
